# WPrism — Adversarial Design Review (v0, 2026-08-04)

> Produced by an independent adversarial review of the v0 design before any code was written.
> Findings 1–27 below are folded into DESIGN.md; this file preserves the full register verbatim.

Adversarial design review of WPrism. WebSearch was used to verify prior-art claims (Mergebot shutdown + schemas repo, VersionPress status + plugin-definition architecture, Pantheon workflow docs); WordPress/plugin internals claims are from model knowledge. Also sent to team-lead via SendMessage.

## A. Provenance classification (task 1)

1. **[critical] Authentication ≠ authorship.** Logged-in customers, students, and members write runtime data through authenticated surfaces constantly: WooCommerce Store API checkout, LearnDash quiz attempts, bbPress/BuddyPress posts, front-end reviews — and admin-ajax.php is technically an admin context (`is_admin()` true) even for subscriber-role requests, a very common legacy plugin pattern. *Fix:* the authored signal must be actor capability (`edit_posts`/`manage_options`) × surface (wp-admin settings POST, editor REST save, customizer save); bare "authenticated" must never propose authored.

2. **[critical] Single requests write mixed classes, so request-scoped provenance cannot classify.** An admin saving a Woo product also writes `_edit_lock`, Action Scheduler job rows, lookup-table rows, and transients in the same request; conversely a checkout writes the order and decrements product `_stock`. *Fix:* journal at (table, key/column) granularity, capture the hook stack (`current_action`) and calling plugin via sampled backtraces, and demote request context to a tie-breaker prior.

3. **[serious] "CLI ⇒ authored" mislabels the standard production cron transport:** `DISABLE_WP_CRON` + system cron running `wp cron event run --due-now` makes all cron writes look like CLI, and wp-cli is equally used for imports, search-replace, and maintenance. *Fix:* classify by executing hook context (inside a cron hook ⇒ cron), special-case `wp cron` subcommands, and require an explicit intent flag for CLI ops meant to be authored.

4. **[serious] Authored-data-via-cron false negatives are business-critical and silent:** scheduled imports/ERP-PIM product syncs (WP All Import etc.), scheduled revision publishing (PublishPress), and email-to-post land authored content in cron context, which the default classifies runtime and never captures. *Fix:* the design's own author axis implies a third class — "externally-sourced, re-syncable per environment" with explicit re-sync semantics — rather than forcing the authored/runtime binary; import/sync plugins' manifests must declare their outputs.

5. **[critical] The conservative default converts uncertainty into invisible data loss.** A site-admin toggles a setting in an unmanifested plugin → queued, unreviewed, absent from the repo → the branch merges "clean" and production behaves differently, discovered only in anger; real sites will queue hundreds of keys in week one, so rubber-stamping or ignoring is the equilibrium. *Fix:* make unclassified state loud and blocking at operation time — capture/merge/apply fail (or demand explicit ack) when in-scope entities have pending-unclassified writes; show unclassified drift in the plan; auto-propose classifications from a soak window (write frequency, anon-write ratio, value churn). The provenance journal is acceptable only as a proposal generator, never as an authority — containment holds only with this gate.

6. **[serious] Journal cost and blind spots:** the wpdb `query` filter fires on every query including reads, cannot observe `insert_id` or rolled-back transactions (phantom provenance), the journal itself is unbounded runtime data, and the mysqli-bypass reconciler implies periodic full-table checksums that lock or lie (`CHECKSUM TABLE` scans; InnoDB `update_time` resets on restart). *Fix:* run provenance as a learning mode that switches to sampling once a key's classification stabilizes; use ledger-vs-DB diff at capture time as ground truth for *what* changed and let provenance only explain *why*. [minor] rider: entropy detection for secrets underperforms pattern denylists (`sk_live_`, `AKIA`, `ghp_`…) and false-positives hashes; use patterns + manifest env-bound defaults first.

## B. Identity / reference rewriting (task 2)

7. **[critical] The ID space is untyped.** `term_id` vs `term_taxonomy_id` are distinct keyspaces used inconsistently (`term_relationships` uses tt_id; options like `default_category` use term_id; pre-WP-4.2 shared-term databases still exist where they diverge), plus posts/users/comments. *Fix:* ledger entries must be (uuid, entity_type, id_kind), and every rewriter declaration must state which kind a field holds.

8. **[critical] "Opaque snapshot" mode is a trap for precisely the tables that need it:** authored custom tables almost always embed local auto-increment refs — WPML `icl_translations` (element_id = post/term IDs), Ninja Forms `nf3_*` (intra-table FKs), Woo attribute taxonomies/shipping zones/tax rates — and Polylang hides serialized post-ID arrays inside the term *description* text column. Pick-side JSONL replay writes env-A IDs into env B: silent corruption, the exact failure class that killed trust in predecessors. *Fix:* refuse opaque mode for tables with FK-like columns (int columns whose values join to posts/terms/users); add a middle tier "typed snapshot" with column-level ref declarations; classify WPML/Polylang as manifest-mandatory, never opaque-eligible.

9. **[serious] Core option refs go far beyond page_on_front:** `sticky_posts` (ID array), `default_category`, `wp_page_for_privacy_policy`, `site_icon`/`site_logo`/`custom_logo`, the serialized `theme_mods_{theme}` blob (`nav_menu_locations` → menu term IDs, `custom_css_post_id`, header/background attachment IDs), widget instances (`widget_*` arrays, the ordered `sidebars_widgets` map, block widgets in `widget_block` containing block HTML), the `woocommerce_*_page_id` family, `elementor_active_kit`. *Fix:* enumerate these in the core manifest, and add a capture-time linter that flags unclassified option values that equal existing post/term IDs.

10. **[serious] Block-level refs beyond `"id":N` and `wp-image-N`:** `wp:block {"ref":N}` (reusable blocks/patterns), `wp:navigation {"ref":N}`, gallery `"ids":[…]`, query-loop taxQuery term IDs, navigation-link `id`, cover media IDs — and block themes store site structure as DB posts (`wp_template`, `wp_template_part`, `wp_navigation`, `wp_block`) which must be first-class authored entities or FSE sites cannot branch at all. *Fix:* a block-rewriter registry keyed by block name with typed attribute paths (including arrays), plus rewriting of href-form internal links (`?page_id=N` and permalink URLs) in block HTML, and explicit support for the FSE CPTs.

11. **[serious] nav_menu internals hit in v0:** `_menu_item_object_id` is polymorphic (typed by `_menu_item_type`: post vs taxonomy vs custom), `_menu_item_menu_item_parent` is a self-referential nav_menu_item post ID, and menu→location assignment lives inside theme_mods, not the menu. *Fix:* polymorphic ref typing in the core manifest and a two-pass apply (create items, then resolve parents), plus theme_mods location handling.

12. **[serious] Schema-driven meta breaks static manifests:** for ACF/Meta Box/Pods, which meta values are IDs is determined by field-group definitions (themselves posts or acf-json files), with IDs stored as strings inside serialized arrays and shadow `_field` keys carrying field-key pointers. *Fix:* manifests need an interpreter capability — the ACF manifest reads the field schema present in the same repo to type meta values at capture/apply; also reconcile DB field-groups vs acf-json sync state.

13. **[serious] Page-builder payloads:** Elementor `_elementor_data` is JSON with escaped URLs (`https:\/\/…`) full of attachment/template/popup/kit IDs and dynamic-tag post refs; Beaver Builder stores PHP serialized *objects* (`O:…`) that will not survive the proposed serialize→JSON→re-serialize round-trip (class fidelity, private props, `__wakeup`). *Fix:* verbatim-preservation path for non-plain-data serializations (keep original bytes; rewrite only via safe in-place token substitution or refuse with a warning), and teach the URL tokenizer JSON-escaped forms.

14. **[serious] Apply ordering is unspecified:** post_parent hierarchies, attachment parents, menu-item parents, reusable-block nesting, and Elementor template refs form a dependency graph with possible cycles. *Fix:* make two-phase apply the engine default — insert all rows with placeholder refs, then a resolve/fixup pass — rather than per-case ordering.

15. **[serious] Direct-SQL apply bypasses derived-state maintainers, not just emails:** Yoast's indexables table, Woo `product_meta_lookup`, `term_taxonomy.count`, `comment_count`, search-index plugins (Relevanssi/SearchWP), and Elementor CSS are all maintained by the very hooks WPrism deliberately skips — applied content renders missing or wrong on B despite correct rows. *Fix:* manifests declare per-plugin "rebuilders" executed in the invalidation pass; the core pass adds term recount, comment recount, and lookup regeneration.

16. **[serious] Apply races live traffic:** direct SQL against a running environment interleaves with runtime writes (stock decrement mid-apply, session rows touching entities being rewritten); the snapshot backup protects against crashes, not interleaving. *Fix:* transactional apply where feasible + an mu-plugin write-gate (brief maintenance window) + per-entity optimistic check against ledger-expected state, with conflicts downgraded into the drift report.

17. **[minor] `guid` is env-bound** (absolute URL, often `?p=<local id>`): keeping it verbatim leaks env A's home URL into canonical files; rewriting it churns RSS consumers. *Fix:* classify guid env-derived — generate deterministically per environment on first apply, pin in the ledger, exclude from diffs.

18. **[minor] Slug collisions across branches:** two branches independently create `/about/` → different uuids, same path; apply auto-suffixes `-2` and permalinks silently diverge between environments. *Fix:* plan-time uniqueness check on (post_type, slug, parent) with an explicit resolution step.

19. **[minor] Users leak beyond post_author:** ACF user fields, plugin options storing recipient/owner user IDs. *Fix:* make the login/email token a general ref type available to all rewriters, with a declared fallback (map to configured default author + plan warning; never auto-create users on apply).

## C. Prior art (task 3) — verified via WebSearch

20. **[critical] Both predecessors built exactly WPrism's manifest layer, and it still killed them.** VersionPress: schema.yml per plugin + VPIDs + a planned community definitions repo that never materialized; archived 2020 as "a great proof-of-concept" needing "several person-years" to finish. Mergebot: a public mergebot-schemas JSON format (PK/FK, serialized-value mappings, shortcodes) plus a schema-generator tool — shut down in 2018 anyway because it couldn't meet their quality bar; for a state-merge tool, 95% correct is negative value because the failing 5% is silent corruption. *Fix:* manifests must be versioned artifacts pinned to plugin version ranges (Woo HPOS moved orders to custom tables and would invalidate any older manifest), backed by a round-trip conformance harness (capture→apply→re-capture = ∅) run in CI against plugin releases, with the product guarantee explicitly scoped to manifested plugins and loud degradation elsewhere — the honest denominator both predecessors lacked.

21. **[serious] The manifest treadmill is a permanent organizational cost, not a launch cost,** and "community manifests" is precisely VersionPress's planned-but-never-realized definitions repo. *Fix:* budget an ongoing manifest team for the top-N plugins and make the provenance/review pipeline *generate draft manifests* (Mergebot built a schema-generator for the same reason) so community contribution is review, not authorship.

22. **[serious] Pantheon/WP Engine's "code up, content down, content freeze" is a deliberate answer, not an oversight:** multidev forks the full stack but editorial changes in a fork never merge back, and it works because environments are short-lived clones of prod. WPrism's long-lived content branches will accumulate unclassified drift against stale runtime backdrops. *Fix:* make "materialize fresh from prod snapshot + apply branch delta" the default feature-env workflow, add branch TTLs, and expose the drift report as a CI status; keep prod-content-is-truth as the default conflict bias.

23. **[minor] Core's own precedent:** WXR import/export is lossy exactly where v0 aims (serialized meta, menu assignments), and wp-cli search-replace proves serialized-length handling is table stakes. This validates the uuid + structure-aware-rewriter bet and capture-time URL tokenization; keep menus in v0 as the canary. No change needed.

## D. v0 spike (task 4)

24. **[serious] The spike never exercises the reason the product exists: merge.** One-way capture→apply is replication, which WP Migrate DB + search-replace already do; prior art died on merge semantics. *Fix:* add a v0 exit criterion — edit X in A, edit Y plus one conflicting field of X in B, capture both, git-merge, apply to both; assert convergence, that the conflict surfaced as a git conflict, and that B-local drift appears in the plan.

25. **[serious] Terms/taxonomies are silently in scope** (menus ARE terms; posts carry categories) but unlisted, and they force the typed-ID question immediately. *Fix:* name terms explicitly in the v0 entity set and build the (uuid, entity_type, id_kind) ledger from day one — retrofitting typing means migrating every ledger.

26. **[minor] "Options" unbounded is the tar pit** (serialized widgets, theme_mods, env-bound keys). *Fix:* whitelist ~8 options for v0 (`blogname`, `blogdescription`, `show_on_front`, `page_on_front`, `page_for_posts`, `sticky_posts`, `default_category`) — still forces option→post/term rewriting without the serialized ocean; explicitly exclude widgets/customizer from v0.

27. **[minor] "No mails/webhooks fired" is trivially true under direct SQL and proves little;** the meaningful claims are "zero WP hooks fired during apply," "capture is deterministic," and "derived state got rebuilt." *Fix:* canary mu-plugin asserting zero fires on `save_post`/`transition_post_status`/`created_term`/`wp_insert_comment` + mail/HTTP interceptors; add acceptance checks: capture A twice → zero diff, and B's category archive actually renders the applied post with correct term counts. Also: post_author is unavoidably in v0, so implement the user-token fallback (missing user → configured default author + warning) now.

**Overall verdict:** the partition/ledger/plan-apply core is sound and genuinely improves on prior art (selective partition vs VersionPress's capture-everything; tokenized URLs vs search-replace). The two existential risks are (a) silent authored-data loss via the unreviewed queue (finding 5) and (b) the manifest treadmill under an absolute reliability bar (finding 20). Both demand the same posture: loud, blocking, scoped guarantees instead of quiet best-effort.
