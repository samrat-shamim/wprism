# Frontier gap report — Polylang

*Explored on the dedicated `fx` env pair (fx1 `:8810` / fx2 `:8811`, docker-compose profile `fx`), reset to clean-room between topics (fresh WP install + fresh site repo). No edits to `agent/src/**` or existing manifests — everything here is site-policy overrides plus empirical observation.*

## Environment facts

- WordPress 7.0.2, PHP 8.3, MariaDB 11, theme `twentytwentyone` (classic, non-FSE — irrelevant to this topic).
- **Polylang (free) 3.8.6**, `wordpress.org` slug `polylang`, installed via `wp plugin install polylang --activate` on both envs.
- Polylang free ships **no wp-cli commands** (`wp help pll` → "'pll' is not a registered wp command"). This forced seeding through Polylang's own PHP API rather than a CLI recipe — see below.
- Version 3.8.x uses a modern namespaced/PSR-4 source layout (`src/Model/Languages.php`, `WP_Syntex\Polylang\Model\Languages::add()`), not the older `PLL_Admin_Model::add_language()` naming that appears in most tutorials and my own initial recollection — worth flagging since anyone building a Polylang manifest off memory or old docs will grep for the wrong symbol.

## Seeding method

I did **not** guess Polylang's internal storage shape from memory — every claim below was checked by grepping the installed plugin's actual source before writing a line of seed code, and every DB claim was checked by direct query. Seeded via `wp eval-file` calling Polylang's **documented public API** (`src/api.php`), the same functions a real integration would use:

1. Two languages: `PLL()->model->languages->add(['locale'=>'en_US','slug'=>'en','name'=>'English'])` and the French equivalent.
2. A translated post pair: two `wp_insert_post()` calls, then `pll_set_post_language()` + `pll_save_post_translations(['en'=>$id_en,'fr'=>$id_fr])`.
3. A translated term pair: two `wp_insert_term()` calls (category), then `pll_set_term_language()` + `pll_save_term_translations()`.
4. The English post tagged with the English category, the French post with the French category (ordinary `wp_set_post_terms()`).

This is high-fidelity seeding — it's Polylang's own public API, not a hand-rolled approximation — so the DB shape below is exactly what a real site editing through wp-admin would produce, modulo UI-only affordances (bulk translation, the language switcher widget) I didn't touch.

## Findings

| Surface | Observed | Classification / engine need |
|---|---|---|
| **Baseline: capture with Polylang's taxonomies *not* in site policy** | `duo capture` **succeeds cleanly**, zero warnings, zero errors: `captured 2 posts, 4 terms...`. The two posts and four categories (`Uncategorized`/`Uncategorized-fr`/`News`/`Actualites`, see below) are captured as ordinary content with **zero trace** of language or translation-group membership. Two identically-titled "Uncategorized" categories, captured under different slugs, read as two unrelated categories. | This is design finding #5's "silent authored-data loss" risk, live: nothing aborts, nothing warns, the repo just quietly doesn't contain the site's most structurally important fact (which content is which language, and which pairs translate each other). Confirms the loud-gate's blind spot: **it only fires on unclassified post_meta** — an entire *taxonomy* being out of policy scope is not loud at all, it's invisible. |
| Polylang auto-creates content you didn't ask for | Adding the French language alone (before I created anything else) caused Polylang to silently create a second "Uncategorized" category (`uncategorized-fr`) and group it with the original via a `term_translations` relationship — confirmed by term IDs (7 and 1) predating my own explicit `wp_insert_term()` calls (10, 11). | Not an engine gap — a seeding-fidelity/scope note: any Polylang capture strategy has to expect *more* translation groups to exist than an admin explicitly created, from day one of activation. |
| `language` taxonomy term `description` | PHP-serialized array of **plugin config, not refs**: `a:3:{s:6:"locale";s:5:"en_US";s:3:"rtl";b:0;s:9:"flag_code";s:0:"";}`. Captured (once the taxonomy is in policy) as an opaque string via `tokenize_text()` — no `maybe_unserialize`, no `assert_plain`, because `Capture::build()`'s term-file loop never unserializes `description` at all, it treats it as plain text unconditionally. | **Benign in this specific case** (no post/term ids inside), but only by luck of what this taxonomy happens to store — see the next two rows for the same mechanism holding something dangerous. |
| **`post_translations` / `term_translations` term `description`** — design finding #8's predicted shape, confirmed byte-for-byte | `post_translations`: `a:2:{s:2:"en";i:1;s:2:"fr";i:2;}` — a raw PHP-serialized map of **local, environment-bound post ids**. `term_translations`: `a:2:{s:2:"en";i:10;s:2:"fr";i:11;}` — same shape, **local term ids**. Captured verbatim as an opaque JSON string (same code path as above — `description` is never parsed, just tokenized as text, and the raw bytes contain no `{{home}}`/`{{uploads}}` substrings for the tokenizer to catch, so it passes through **100% unchanged**). | **Confirmed active corruption on apply**, not just theoretical (see round-trip section below). The engine has zero concept of "this string is secretly a serialized ref map" — it needs exactly what design finding #13's Elementor discussion calls for in JSON form, generalized to PHP-serialize: a declared, typed **rewriter for a specific taxonomy's `description` column** that unserializes, walks a `{lang_slug: local_id}` map, rewrites each id through the ledger, and re-serializes byte-compatibly (PHP `serialize()`, matching lengths — same "verbatim-preservation vs. safe structural rewrite" fork design finding #8 already anticipated, now with a concrete target). |
| **The `post_translations`/`term_translations` corruption, applied and observed** | Pushed fx1 → cloned to fx2 → `duo apply --adopt-by-slug=terms,posts`: canary **"clean"**, zero warnings. fx1's post ids (en=1, fr=2) happened to match fx2's post ids after apply (coincidence — a single `post/` directory, matching creation order), so `pll_get_post_translations(1)` on fx2 **accidentally** still returns the right thing. fx1's *term* ids (News=10, Actualites=11) did **not** survive: fx2 assigned News=3, Actualites=4 (fx2 already had a pre-existing "Uncategorized"=1 adopted, then created uncategorized-fr=2 first). The stale `term_translations` description (`{"en":10,"fr":11}`) now names fx2 term ids 10 and 11 — which on fx2 are **not categories at all**, they're two of Polylang's own `term_translations`/`post_translations` *group bookkeeping terms* (verified: `get_term(11)` on fx2 returns a `term_translations`-taxonomy term, `pll_6a730be56e50a`). | Directly analogous to the FSE report's navigation-link finding, but sharper: this doesn't just point at the wrong *entity*, it points at Polylang's own internal plumbing, which is exactly the kind of self-referential mess that risks confusing the plugin's own code (loops expecting only content terms, list-table queries, etc.), not just rendering wrong. Confirmed via Polylang's own API: `pll_get_term_translations(3)` (fx2's *real* News term id) returns an **empty array** — Polylang itself has no idea News has a French translation on fx2. |
| **The deeper root cause of that empty array — term-to-term relationships are invisible to Duo, categorically** | Traced precisely: Polylang links a *term* to its translation group via an ordinary `wp_term_relationships` row where **the term itself is `object_id`** (e.g. `object_id=10 (News), term_taxonomy_id=12 (the term_translations group)`) — the *exact same table* posts use to carry their category/tag memberships, just with a term instead of a post in the `object_id` column. `Capture::build_post()`'s relationship-capture loop only ever runs for **posts** (`if ($taxes && !$isAttachment)`, querying `term_relationships WHERE object_id = $postId`); there is **no code path anywhere in `Capture.php` that queries a term's own memberships in other taxonomies.** So even independent of the description-blob corruption above, the relationship that actually drives Polylang's own lookup (`pll_get_term_translations()`) was never captured, never in the state tree, and never recreated by apply — full stop. | **A new, general engine capability, not a Polylang-specific patch:** term-to-term taxonomy relationships (term-as-object) need the same treatment posts already get — a `terms` field on the *term* entity file itself (a term's own membership in other taxonomies), captured and applied symmetrically to how a post's `terms` field works today. This is bigger than Polylang: it's the only way *any* plugin that relates terms to terms (translation groups being the clearest example) can ever be representable. |
| **Object-id collision cross-contaminates captured POST relationships — the sharpest, most general finding of this exploration** | Confirmed with certainty, not inferred: post_en has `ID=1`. The pre-existing "Uncategorized" **category term** also has `term_id=1` (WordPress mints both from independent auto-increment counters, so this collision is inevitable on any real site, not a contrived edge case). `Capture::build_post()`'s relationship query is `SELECT ... FROM term_relationships tr ... WHERE tr.object_id = %d AND tt.taxonomy IN (<all policy taxonomies>)` — it filters by **raw numeric id only**, never by whether the taxonomy's registered `object_type` actually includes posts. Uncategorized-the-*term* (id=1) has its own, unrelated `term_language`/`term_translations` memberships (from the finding above). Because post_en's id is *also* 1, Duo's query for post_en's relationships **matched Uncategorized's term-to-term rows too**, and silently folded them into post_en's captured `terms` field: `"term_language": ["<uuid of pll_en>"], "term_translations": ["<uuid of Uncategorized's group>"]` — relationships that describe **a completely different object** and were never true of post_en on fx1 at all. | **Confirmed as active, written corruption, not just a stale reference:** applying this to fx2 **wrote a real `wp_term_relationships` row** claiming fx2's post_en (also id=1, by more coincidence) belongs to `term_language=pll_en` and `term_translations=pll_6a730be549921` — fabricated relationships that exist in fx2's database now, sourced from a completely unrelated term on fx1. **This is not Polylang-specific.** It will happen on *any* site the moment site policy scopes in *any* taxonomy whose relationships are term-to-term rather than post-to-term, because posts and terms share an overlapping id-space by construction. The fix belongs in the same place as the missing capability above: relationship capture needs to filter by the taxonomy's actual registered `object_type`, and/or split post-object and term-object relationship capture into genuinely separate, type-checked queries rather than one query keyed on a bare integer. |
| Round-trip byte-diff as a correctness proxy, again | Re-capturing fx2 after apply and diffing against fx1's original capture: **byte-identical, clean diff.** Both the stale-id corruption and the fabricated post↔term-translation-group relationship survive a full capture→apply→re-capture cycle completely undetected by Duo's own determinism check, for the same structural reason as the FSE report: the wrong bytes get written once, then faithfully read back. | Second independent confirmation (after FSE) that byte-diff round-tripping cannot be the only correctness gate for any manifest touching values the tokenizer doesn't understand. Strengthens that cross-cutting recommendation rather than introducing a new one. |
| Cache/hook staleness after hook-free apply (a hypothesis that turned out **wrong** — reported for honesty) | I expected Polylang's own language-list cache (`polylang` option, `_transient_pll_languages_list`) to go stale after Duo's hook-free `$wpdb` writes, since Polylang normally updates its cache via `created_term`/etc. hooks that Duo's apply deliberately never fires. Checked directly: `pll_languages_list()` on fx2 correctly returned `['en','fr']` immediately after apply, no rebuild step needed. | **Not a gap.** Worth stating plainly rather than only reporting the scary findings — Polylang's language list resolution turned out to be resilient to the hook-free write path in this version. |
| The `polylang` option | A single flat option (`update_option('polylang', [...])`, 369 bytes as JSON-rendered) mixing: authored config (`force_lang`, `hide_default`, `rewrite`, `redirect_lang`), a plain string ref that's actually safe (`default_lang` — a language *slug*, not a numeric id), a currently-empty but ref-bearing field (`nav_menus` — would hold per-location per-language menu term ids once nav menus are configured), and a purely env-local field (`first_activation`, a unix timestamp of when the plugin was activated *on this environment* — meaningless, arguably wrong, to propagate). | Duo's option classification is whole-option granular (authored/runtime/env/derived), with no sub-key model. This option cannot be safely classified as a single unit — it needs exactly the sub-key option support already tracked as **backlog item #11** ("sub-key option refs + id-keyed arrays"). This exploration gives that backlog item a concrete, real-world forcing example rather than a hypothetical one. |
| postmeta / termmeta | Checked directly: Polylang writes **zero** postmeta and **zero** termmeta anywhere in this seed. Its entire model is taxonomy-based. | Nothing to classify here — simplifies the manifest surface, but means none of the corruption above can be worked around by the usual "add a post_meta rule" playbook; the fixes have to happen at the taxonomy/relationship layer. |

## Proposed next task

**"Term-to-term relationships + typed serialized-description rewriting"** (two engine capabilities, one plugin forcing both):

1. **Term-object relationship capture/apply**, symmetric to what posts already get: a term entity's own membership in *other* taxonomies (as `object_id`), captured into (and reconciled from) its own entity file — the same shape as a post's `terms` field, but on the term side. This alone would fix `pll_get_term_translations()` returning empty.
2. **Object-type-checked relationship queries**: `Capture::build_post()`'s relationship query must filter by the taxonomy's registered `object_type` including `'post'` (or the specific post type), not just raw `object_id` equality — closing the id-space collision that fabricates relationships. This is the highest-priority, most broadly-applicable fix in this report; it's a latent correctness bug independent of Polylang.
3. **A typed rewriter for `term_taxonomy.description`** when a taxonomy's manifest declares it holds a serialized `{lang_slug: local_id}` (or similar) map — unserialize, rewrite each id through the ledger by declared kind (`post` for `post_translations`, `term` for `term_translations`), re-serialize. Structurally the taxonomy-column analogue of the JSON-path work the Elementor report asks for on postmeta.
- **Acceptance criteria:** reseed this report's exact fixture on a fresh env pair (or equivalent — two languages, one translated post pair, one translated term pair). After capture → apply → re-capture: (a) byte-diff clean (already true today), (b) **`pll_get_term_translations()` on the target environment returns the correct pair using the target's own local ids**, (c) **no `wp_term_relationships` row exists on the target relating a post id to a term-only taxonomy** (the collision-fabrication check), (d) `pll_get_post_translations()` returns the correct pair *even when post creation order doesn't coincidentally preserve ids* (extend the fixture with an extra unrelated post/attachment inserted between languages and content, specifically to break the lucky-coincidence case this exploration didn't stress).
- **Guard, cheap to add immediately:** the capture-time linter proposed in the FSE report (flag suspicious bare integers with no declared ref path) should also cover `term_taxonomy.description` — it would have caught the `post_translations`/`term_translations` case for free, the same way it would have caught `core/navigation-link`.

## Draft manifest

**None shipped.** Polylang writes zero postmeta/termmeta (checked directly), so there is no "safe subset" of classification rules to offer the way FSE's `origin` meta or ACF's field-type rules provide one — every substantive piece of Polylang's data model (the taxonomies' relationship graph, the serialized description maps, the un-sub-keyable `polylang` option) requires an engine capability that doesn't exist yet. Shipping a `polylang.draft.json` today would either be empty (misleading — implying readiness that isn't there) or would recommend site-policy taxonomy scoping that is now *known*, empirically, to actively corrupt data on apply. Recommending against enabling this manifest at all is the honest output of this exploration.

## Verdict

Polylang is the **furthest of the three frontiers from branchable**, and by a wide margin. FSE's and Elementor's gaps are narrow and mechanical (extend a schema, add a rewriter). Polylang's core problem is structural: its central mechanism — term-to-term relationships carrying translation-group membership — sits entirely outside a data model Duo built assuming taxonomy relationships always point *from* a post *to* a term. Worse, this exploration surfaced a general-purpose engine bug (the object-id collision between posts and terms silently fabricating relationships) that has nothing to do with Polylang specifically and would eventually bite any site whose policy scopes in a term-to-term taxonomy — Polylang just happened to be the frontier that forced it into the open. That bug alone justifies triaging it ahead of, and independent from, either of this session's other two reports.

## Status update (task #20): shipped

Both capabilities this report called for are built, and Polylang now has a shipped manifest. Acceptance criteria (a)–(d) all pass on a fresh conf1/conf2 pair (`bash sandbox/conformance/run.sh polylang`, clean-room, hard lint gate included), and `sandbox/tests/live/regress_collision.sh` (now pinning `["core", "polylang"]`, not just `["core"]`) proves the #19 collision fix and both new capabilities hold together on the exact engineered post↔term id collision this report found.

**Capability 1 — term-object relationship capture/apply.** Term entity files gain a `relationships` field: `{"<taxonomy>": ["<term-uuid>", ...]}`, always present (an object, `{}` when empty — the exact symmetry of a post's `terms` field). `Capture::taxes_by_object_type()` (renamed/generalized from `taxes_for_post_types()`) now computes, in one `get_taxonomy()` walk, both the existing post_type→taxonomy map AND the list of taxonomies whose registered `object_type` is literally `["term"]` — confirmed empirically on a fresh install that Polylang's `term_language`/`term_translations` register exactly that shape, while `language`/`post_translations` register post types (`post`/`page`/`wp_block`). `Capture::term_relationships()` queries `term_relationships WHERE object_id = <this term's own term_id> AND taxonomy IN (<term-object taxonomies>)`, resolves each target through the ledger, sorts for determinism. `Apply::reconcile_term_relationships()` mirrors `reconcile_relationships()` exactly (create missing rows, delete extra rows, scoped to the same object-type-filtered taxonomy list) and runs from `finalize_term()` — two-phase-safe for free, since phase 1 already inserts every term row (source and target) before any `finalize_term()` call. An unregistered taxonomy still warns loudly and skips (posture unchanged from #19), now naming both posts and terms in the warning. Delete symmetry was added too: `Apply::delete_term_relationships()` mirrors `delete_post_relationships()`, cleaning up a deleted term's own outbound rows scoped to every *registered* term-object taxonomy (not just policy-scoped ones — same rationale as the post-side twin).

**Capability 2 — typed serialized-description rewriting.** New manifest section, deliberately minimal: `"taxonomies": {"<tax>": {"description_refs": {"kind": "post"|"term"}}}`. Manifest-only (no `site.duo.json` policy override) — a structural fact about the taxonomy's own data shape, like `block_attrs`, not a site-local policy choice; this also sidesteps a real naming collision, since `policy.taxonomies` is already the flat taxonomy-scope list and reusing that key for a name-keyed rule map would silently shadow it. `Policy::description_refs_for_taxonomy()` reads it. `Capture::term_description()` unserializes the raw `term_taxonomy.description` string (WordPress never auto-unserializes this column the way `maybe_unserialize()` does for postmeta/options) and rewrites it with the *existing* `Tokens::struct_capture()` primitive at path `"$.*"` (every top-level value in the flat `{lang_slug: id}` map is a ref of the declared kind; the keys are language slugs, never ids, so no `key_refs`) — zero new rewriting machinery, full reuse as instructed. Canonical shape: the term file's `description` field becomes a native token-bearing object (e.g. `{"en": "{{post:<uuid>}}", "fr": "{{post:<uuid>}}"}`) for declared taxonomies, cast to object so an empty map still encodes as `{}`; every other taxonomy keeps the original opaque tokenized-string treatment unconditionally. `Apply::encode_description()` mirrors it: `Tokens::struct_apply()` then PHP's own `serialize()` — verified byte-exact on a live run, e.g. `a:2:{s:2:"en";i:1;s:2:"fr";i:2;}` with genuinely int-typed values (`i:N;`, never the ACF/Yoast digit-string convention — confirmed no `cast` is declared or needed). Unmapped ids null the scalar per the existing json_refs/#21 semantics (reused verbatim, not reinvented).

**Lint interplay.** `Lint::scan_term_file()` now takes `Policy` and checks `description_refs_for_taxonomy()` first: a declared taxonomy's description is deep-scanned with the *same* `scan_structured_bare_ids()` helper json_refs/key_refs-declared meta/option values already use (declared paths clean, any position the "$.*" path didn't cover still flagged — the identical contract, not a parallel one); an undeclared taxonomy keeps the original unserialize-and-scan-for-int-hits behavior unconditionally. Proven both ways on a live run: with `polylang` unpinned, `wp duo lint` flags `serialized_desc_ids` on the raw `post_translations`/`term_translations` bytes; with it pinned, the same site captures 0 findings.

**The `polylang` option blob: excluded, not guessed.** Verified byte-for-byte on a fresh install (`{"force_lang":1,"domains":[],"hide_default":true,"rewrite":true,"redirect_lang":false,"browser":false,"media_support":false,"post_types":[],"taxonomies":[],"sync":[],"default_lang":"en","nav_menus":[],"first_activation":1785944547,"previous_version":"","version":"3.8.6"}`) — mixes authored config, a currently-empty-but-ref-bearing `nav_menus`, and upgrade-gate/activation-timestamp bookkeeping. Classified `env` and skipped, matching `manifests/yoast.json`'s identical call on `wpseo` for the identical reason: json_refs/key_refs rewrite ref-shaped *values* already known to be captured, they are not a sub-key capture/exclude split, and building that split is a genuinely separate, unscoped engine capability — not invented here to avoid a rushed bolt-on. `pll_language_from_content_available`/`pll_language_taxonomies` (read from Polylang's own `src/install/activate.php`: both `add_option()`'d once at activation, installation-time artifacts, never admin-authored) are classified `runtime`. `polylang_wpml_strings`/`widget_polylang` are left undeclared — both empty in every verified fixture, populated shape never empirically observed, documented as a known gap rather than guessed.

**Manifest**: `manifests/polylang.json` (new). **Conformance**: `sandbox/conformance/manifests.json`'s `"polylang"` entry, `sandbox/conformance/seeds/polylang.sh` (the fixture above, plus anti-coincidence filler posts/categories — created then hard-deleted on conf1 only, so conf1's and conf2's ids for the same uuid are genuinely different and criterion (d) can't pass by luck), `sandbox/conformance/checks/polylang.sh` (live `pll_get_post_translations()`/`pll_get_term_translations()`/`pll_get_term_language()` calls using conf2's own ids, a byte-exact re-serialized-description check, and the render/host-leak convention), `.github/workflows/conformance.yml` matrix line. **Engine**: `agent/src/{Capture,Apply,Policy,Lint}.php`. **Regression**: `sandbox/tests/live/regress_collision.sh` extended with News's own term-file relationship assertions, a live `pll_get_term_translations()` proof on fx2, and the term-side symmetry of the unregistered-taxonomy posture check.
