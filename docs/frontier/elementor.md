# Frontier gap report — Elementor

*Explored on the dedicated `fx` env pair (fx1 `:8810` / fx2 `:8811`, docker-compose profile `fx`), reset to clean-room between topics. No edits to `agent/src/**` or existing manifests — everything here is site-policy overrides (including via the new `wp duo classify` command, which landed mid-session — see below) plus empirical observation.*

## Environment facts

- WordPress 7.0.2, PHP 8.3, MariaDB 11, theme `twentytwentyone` (classic — irrelevant to this topic).
- **Elementor (free) 4.2.1**, `wordpress.org` slug `elementor`, installed via `wp plugin install elementor --activate`.
- Activation alone creates one `elementor_library` post (`Default Kit`, uncustomized) and sets `elementor_active_kit` (a plain option holding that post's raw local id) plus several bookkeeping options (`elementor_version`, `elementor_checklist`, etc.).

## Seeding method (and an honest account of how hard it was to get right)

The Elementor editor is a heavy client-side JS application (iframe-based drag-and-drop) with no wp-cli surface at all — driving it headlessly was never on the table. Per the brief, I seeded `_elementor_data` via `wp eval`, but went one step further than "realistic hand-written JSON": I called **Elementor's own save pipeline** — `\Elementor\Plugin::$instance->documents->get($post_id)->save(['elements' => [...]])` — the same code path the editor itself calls, rather than writing to `_elementor_data` directly. This means the byte shape reported below is exactly what Elementor produces, not my approximation of it.

Getting there took three failed attempts, each instructive enough to mention rather than bury:
1. First `save()` call returned `false` with no exception — turned out `settings` must be a plain PHP array for *every* element, including empty ones; I had used `new stdClass()` for an empty settings object (reasoning it'd encode to JSON `{}`), which crashes Elementor's internal `sanitize_settings(array $settings)` type check the moment it actually has content to walk. Fixed by using `[]` uniformly.
2. My seed script hardcoded the uploaded image's filename across reruns; a partial cleanup between attempts (deleting an "orphaned" attachment post) collaterally deleted the physical file a *different* attachment's `_wp_attached_file` meta also pointed at, because both attempts had written to the identical literal path. Fixed by generating a random filename suffix per run.
3. Worth flagging as its own small finding: `wp_insert_attachment()`'s auto-generated `post_name` (from title) and the literal filename passed to it are **independent** — a slug collision auto-suffixes the post's slug but does *not* change `_wp_attached_file`, which is exactly the kind of divergence between "human-readable identity" and "actual storage path" this whole project is built to handle correctly; it just wasn't the file I intended to test.

None of this is an Elementor or Duo finding — it's a caveat about my own seeding fidelity, included because the brief specifically asked for honesty here rather than a clean narrative.

The final fixture: a link-target page, a GD-generated image attachment, and an Elementor-built page containing one `image` widget (referencing the attachment by id) and one `button` widget with an internal link (the target page's permalink, entered as a plain URL — see below for why that matters).

## Findings

| Surface | Observed | Classification / engine need |
|---|---|---|
| `_elementor_data` shape, verified at the byte level (not just visually) | `[{"id":"ca97f2f","elType":"section","settings":[],"elements":[{"id":"8d3e0bc","elType":"column","settings":{"_column_size":100},"elements":[{"id":"d69cb7b","elType":"widget","settings":{"image":{"id":10,"url":"http:\/\/localhost:8810\/wp-content\/uploads\/2026\/08\/duo-elementor-hero-f5fca5b9.png"}},...},{"id":"f0e8366","elType":"widget","settings":{"text":"Learn more","link":{"url":"http:\/\/localhost:8810\/duo-elementor-target\/",...}},...}]}]}]` — a JSON *string* in postmeta, `wp_json_encode()`'d **without** `JSON_UNESCAPED_SLASHES`. Confirmed via `xxd`: the bytes are `5c 2f` (one literal backslash, `0x5c`, then `/`) — genuinely JSON-escaped, not a display artifact. The image widget carries a bare numeric attachment id (`"id":10`) *and* a redundant absolute URL; the button's internal link carries **only** a URL string, no post id at all — entering a link as a plain URL (rather than using Elementor's separate "Dynamic Tags" post-reference feature, not exercised here) means Elementor itself doesn't know it's "internal." | Exactly design finding #13's predicted shape, now measured rather than assumed. Two independent problems bundled in one field: a **numeric id** needing ledger remapping (`image.id`), and a **JSON-escaped absolute URL** needing tokenization (`image.url`, `link.url`) that today's plain-string tokenizer cannot reach (see next row). |
| **DESIGN.md's documented tokenizer claim does not match the shipped code** | `DESIGN.md` §3.3 states outright: *"The tokenizer also understands JSON-escaped URL forms (`https:\/\/…` inside `_elementor_data`-style meta)."* Checked `agent/src/Tokens.php::tokenize_text()` directly: it is `str_replace($this->home, '{{home}}', $s)` — a **literal, unescaped** substring match. It cannot and does not match `http:\/\/localhost:8810` (escaped) against `http://localhost:8810` (the raw `home` option value) — confirmed by capturing the fixture above and observing the URL pass through **completely unchanged**, escaped slashes and all. | **This isn't a new capability to design — it's a documented capability that was never implemented.** The fix is bounded and already specified in prose: `tokenize_text()`/`detokenize_text()` need an escaped-slash-aware mode (match both `http://host` and `http:\/\/host` forms), engageable wherever a manifest declares a meta value should get JSON-escaped-URL treatment. |
| Capture's `assert_plain()` guard | Classifying `_elementor_data` as `authored` (no `ref`) and capturing does **not** trip `assert_plain()` — the guard only rejects PHP **objects** (Beaver-Builder-style `O:...` serialized classes); `_elementor_data`'s value is a plain string (valid JSON text, but opaque to `maybe_unserialize()`, which just returns strings unchanged when they don't match PHP's serialize format). So capture **succeeds silently**, with no warning of any kind, embedding the raw bytes verbatim. | Confirms design finding #13's fork applies asymmetrically: Elementor's JSON payload sails through the guard that exists to catch Beaver-Builder-style PHP objects, because it's the wrong shape of danger for that specific guard. The verbatim-preservation path discussion in the spec is about **whole `post_content` bodies** (`"body": "verbatim"` in manifest `post_types`); there is no equivalent per-*meta-key* verbatim/typed-rewrite mechanism, and `_elementor_data` lives in **postmeta**, not `post_content` — the existing verbatim-body machinery is structurally the wrong shape for this even if it were extended. |
| The loud-gate, precisely | `duo capture` aborts listing exactly seven keys: `_elementor_data`, `_elementor_edit_mode`, `_elementor_global_class_usage_indexed`, `_elementor_global_class_usage_indexed_preview`, `_elementor_page_assets`, `_elementor_template_type`, `_elementor_version`. All resolved via **the new `wp duo classify --repo=<repo> --set='section:key=class'`** command (landed mid-session from the concurrent "core loop engine" work) — classified `_elementor_data`/`_elementor_edit_mode`/`_elementor_template_type` authored, `_elementor_version` managed, the rest derived. One usage note for whoever documents that command: `--set "value"` (space-separated) silently gets parsed as a bare boolean flag by wp-cli's own argument parser, producing a confusing `bad --set spec '1'` error; it must be `--set=value` (equals-joined). | Manifest-shaped work, now done — see the draft manifest below. Confirms the loud-gate does exactly its documented job here: nothing silently entered the repo. |
| **Elementor lazily creates *more* derived metadata on first front-end render** — an organic, unplanned discovery | fx1 was captured without ever being visited on the front end. After applying to fx2 and `curl`-ing the rendered page (to check the corruption below), re-capturing fx2 hit a **second** loud-gate abort for three keys that didn't exist on fx1 at capture time: `_elementor_css`, `_elementor_element_cache`, `_elementor_migrations_state_d2a1`. These are generated the first time Elementor renders a given page (CSS compilation cache, element cache, a migration-state marker), not at save time. | Classified `derived` (all regenerable) and moved on, but the finding itself matters independent of the fix: **a manifest built from testing against one environment's history can under-classify a second environment that has been "visited" differently.** A conformance harness for this manifest needs a rendering step (viewing the page at least once) before its second capture, or it will falsely believe the manifest is complete. |
| **A second, distinct engine gap surfaced by that same key: `post_meta`/`term_meta` classification has no pattern-matching escape hatch** | The `d2a1` suffix on `_elementor_migrations_state_d2a1` reads as a version- or hash-derived identifier, not a stable literal — plausibly `_elementor_migrations_state_<a different hash>` on another Elementor release or even a different site. Checked `Policy::rule()` directly: the `option_patterns` regex-fallback mechanism (`core.json` already uses it for `^_transient_` etc.) is gated `if ($section === 'options')` — there is **no equivalent for `post_meta` or `term_meta`**, only exact-string lookups. | A real, if narrower, gap independent of Elementor's content-corruption problems above: any plugin using versioned or hashed meta-key suffixes can never be fully pre-classified by a shipped manifest — every differing suffix reopens the loud-gate on every site, forever. Worth a `meta_key_patterns` sibling to `option_patterns`, scoped carefully (unlike option names, meta keys are per-entity-type, so it would need a "which post types this pattern applies to" dimension `option_patterns` doesn't need). Included in the draft manifest below as a literal-key stopgap — harmless if it doesn't match elsewhere (a non-matching site just sees the ordinary loud-gate, not a corruption risk) but not a real fix. |
| **The corruption, applied and rendered — confirmed, not inferred** | Pushed fx1 → cloned to fx2 → `duo apply` (canary "clean", zero warnings) → fx2's local ids diverged from fx1's (attachment became id 2, not 10 — `get_post(10)` on fx2 returns nothing at all, a dangling reference rather than even a wrong-type collision). Elementor's front-end renderer reads `_elementor_data` (not the parallel `post_content` — see next row), so this is exactly what a real visitor would see. | Direct confirmation of the JSON-escaped-URL gap's real-world consequence, structurally identical to the FSE and Polylang reports' findings: an id that no longer resolves to the right thing, plus an absolute URL that leaks the source environment. |
| **A subtle, worth-flagging asymmetry: the visible content looked fine** | Elementor also writes a plain-HTML `post_content` "fallback" alongside `_elementor_data` (used by feeds, search indexing, and non-JS contexts). This HTML is **not** JSON-escaped, so Duo's *existing* content pipeline handled it correctly: `<img src="{{uploads}}/.../duo-elementor-hero-f5fca5b9.png">` and `<a href="{{home}}/duo-elementor-target/">` both tokenized and re-bound correctly on fx2. | Anyone eyeballing the captured `post_content` for this page would see it looking perfectly tokenized and reasonably conclude Elementor "just works." The actual rendering source (`_elementor_data`) is the one that's broken, and it's invisible unless you specifically inspect the meta. Worth stating for whoever scopes the next task: **do not use `post_content` as your correctness check for a page-builder manifest** — it can look right while the plugin renders wrong. |

## Proposed next task

**"JSON-escaped-URL and JSON-path id rewriting for postmeta values"** — implementing what `DESIGN.md` already describes, plus what it doesn't:

1. **Escaped-slash-aware tokenization**, exactly as documented: extend `Tokens::tokenize_text()`/`detokenize_text()` (or add a sibling pair) to match `{{home}}`/`{{uploads}}` against both the raw and `\/`-escaped forms of the configured URLs, engaged per meta key via a manifest declaration (e.g. `"post_meta": {"_elementor_data": {"class": "authored", "text_mode": "json-escaped"}}`).
2. **JSON-path id-ref declarations for postmeta** — the DESIGN.md-mentioned but unbuilt capability: a manifest declares, for a given meta key, one or more JSON paths into the decoded value that hold ids of a given ref kind (e.g. `elements[].elements[].elements[].settings.image.id` → `post`), walked recursively across Elementor's arbitrarily-nested `elements` arrays (sections → columns → widgets, and widgets can themselves nest via `elements: []`), rewritten through the ledger the same way block attrs are today, then re-encoded with `wp_json_encode()` (matching Elementor's own missing-unescaped-slashes convention so the round-trip stays byte-faithful).
3. **Acceptance criteria:** reseed this report's fixture (image widget + internal-link button) on a fresh env pair; capture → apply → **render** the target environment's page (not just byte-diff) must show the target's own host in both the image `src` and the button `href`. Extend the fixture with a *second* page linked via Elementor's "Dynamic Tags" post-reference feature (not exercised in this session) to verify the id-shaped case independent of the URL-shaped case.
4. **Guard:** the generalized capture-time linter proposed in the FSE and Polylang reports (flag suspicious bare integers / absolute-URL-shaped strings with no declared rewrite path) should specifically scan JSON-parseable postmeta values too, not just block attrs and taxonomy descriptions — this is the third frontier in a row where it would have caught the gap for free.
5. **Process note, cheap to act on immediately:** correct or implement the DESIGN.md §3.3 claim about JSON-escaped URL tokenization — right now it's documentation of an intention, stated as if already shipped.

## Draft manifest

`manifests/elementor.draft.json` (new file, unvalidated) captures the classification rules verified working in this session: the seven page/kit postmeta keys and the `elementor_active_kit` option. It deliberately does **not** claim the `_elementor_data`/`_elementor_css` content is safe to round-trip across environments — classifying `_elementor_data` as `authored` here is necessary just to get past the loud-gate and observe the *next* problem, not a recommendation to ship. Per the FSE report's scope finding (manifests can't declare post_type/taxonomy scope), a consuming `site.duo.json` also needs its own `policy.post_types` including `elementor_library` and `policy.options` including `elementor_active_kit` — this manifest alone is not sufficient to activate.

**Do not treat this manifest as safe for sites with any internal links or image references in Elementor content** — which is to say, essentially no real Elementor site — until the JSON-escaped-URL and JSON-path id-rewriting work above lands.

## Verdict

Elementor sits **between the other two frontiers**: closer to FSE than to Polylang, because its gap is a single, well-bounded, already-partially-specified capability (JSON-escaped text + JSON-path id refs for one postmeta value shape) rather than Polylang's structural blind spot (a relationship type the data model has no room for) or its general-purpose engine bug (the object-id collision). The clearest evidence for "closer to FSE": the kit post and its option ref worked perfectly today, zero new code, the moment policy declared them — exactly like three of FSE's four content types did. The hardest blocker is genuinely just the one thing: `_elementor_data`'s combination of JSON-escaped absolute URLs and deeply-nested numeric ids, sitting in postmeta rather than `post_content`, where none of the existing rewriting machinery (block attrs, verbatim body mode) structurally reaches.
