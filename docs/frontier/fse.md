# Frontier gap report — FSE (block themes)

*Explored on the dedicated `fx` env pair (fx1 `:8810` / fx2 `:8811`, docker-compose profile `fx`), own site repo (`sandbox/siterepo/{origin-fx.git,fx1,fx2}`). No edits to `agent/src/**` or existing manifests — everything here is site-policy overrides inside `siterepo/fx1/site.duo.json` plus empirical observation.*

## Environment facts

- WordPress 7.0.2 (`wordpress:php8.3-apache` / `wordpress:cli-php8.3`), PHP 8.3, MariaDB 11.
- Theme: **twentytwentyfive 1.5** — a full block (FSE) theme, bundled with core and active by default on a fresh install (no `theme install` needed). `twentytwentyfour` 1.5 and `twentytwentythree` 1.6 are also bundled but inactive.
- Core registers four FSE post types unconditionally, independent of the active theme: `wp_template`, `wp_template_part`, `wp_navigation`, `wp_block` — plus three FSE-specific taxonomies: `wp_theme` (object types: `wp_template`, `wp_template_part`, *and* `wp_global_styles`), `wp_template_part_area` (object type: `wp_template_part`), `wp_pattern_category` (object type: `wp_block`). None of the three taxonomies have any pre-registered terms — they're created on demand, same as `category`/`post_tag`.
- An unmodified block theme's default templates are **not** DB rows at all (synthesized from the theme's `templates/*.html` files); a `wp_template`/`wp_template_part` row only exists once something customizes it. Confirmed by querying before seeding: zero rows in any of the four FSE post types on a fresh install.

## Seeding method (and its honesty limits)

Seeded via `wp eval-file` (`agent`-adjacent direct PHP, not through the Duo agent) doing exactly what Site Editor's REST controllers do under the hood — `wp_insert_post()` + `wp_set_post_terms()` — rather than driving the Site Editor UI or hitting `/wp/v2/templates` etc. over REST:

1. Two pages (`duo-fse-about`, `duo-fse-contact`).
2. A GD-generated image attachment (same technique as spike A/E).
3. A reusable block / pattern (`wp_block`, post_name `duo-fse-cta`) tagged with a `wp_pattern_category` term.
4. A block-based navigation (`wp_navigation`, post_name `duo-fse-primary-nav`) with three `core/navigation-link` children: two `kind:"post-type"` links (to the two pages, by numeric `id`) and one `kind:"custom"` link (external URL).
5. A customized **"home" `wp_template`**, tagged with the `wp_theme` term for `twentytwentyfive`, embedding: a `core/template-part` reference (by slug+theme, not id), the `core/navigation` block (`{"ref":N}` to #4), a `core/image` block (`{"id":N}` to #2), and a `core/block` reusable-block embed (`{"ref":N}` to #3).
6. A customized **"footer" `wp_template_part`**, tagged with both `wp_theme` and `wp_template_part_area` (`footer`) terms, containing a plain paragraph with an `<a href>` permalink to the Contact page.

**Fidelity caveat, stated plainly:** this is not the real Site Editor save path, and a few Site-Editor-only behaviors were *not* exercised: `wp_pattern_sync_status` postmeta (full/partial/unsynced pattern sync mode), autosave/revision churn while editing in Site Editor, and multi-specificity template hierarchies (e.g. `single-post` vs `single`). Where I *did* make claims about DB shape (which taxonomy holds what, which postmeta exists), I verified them by direct query against the running site rather than by assumption — in one case this **overturned my own working hypothesis** (see the template-part-area finding below).

## Findings

| Surface | Observed | Classification / engine need |
|---|---|---|
| `wp_template` / `wp_template_part` / `wp_navigation` / `wp_block` as post types | Not in the default core manifest's `post_types`. Adding them to site policy is *sufficient* — Capture/Apply already treat any post type uniformly (uuid mint, ledger, block-content rewriting via the existing block registry). | **Manifest-only.** No engine change. |
| `wp_theme` taxonomy (templates/parts/global-styles → active theme) | Not in default `taxonomies`. Adding it works mechanically: a normal term gets minted/matched by slug like any other taxonomy term. | **Manifest-only, but with a modeling wart:** the term's real identity *is* the theme's code-slug (already portable on its own), so minting a UUID/ledger row for it is redundant busywork rather than a correctness problem. More importantly, **there is no active-theme-mismatch guard** — if the target environment's active theme differs from the captured `wp_theme` term's slug, the applied template silently becomes inert (WP's template resolver just never matches it) with zero warning anywhere in the plan or apply output. |
| `wp_template_part_area` (header/footer/sidebar/uncategorized) | **A genuine taxonomy**, not postmeta — verified directly (`wp post meta list` on the footer part returned *zero rows*). This overturned my own initial assumption (a `_wp_template_part_area` meta key, which is what I expected from memory going in). | **Manifest-only** — add to `taxonomies`. Worth flagging in case others carry the same wrong assumption forward. |
| `wp_pattern_category` (pattern/reusable-block categorization) | Ordinary taxonomy, rounds-trips generically once added to policy. | **Manifest-only.** |
| `origin` postmeta on a customized-default `wp_template` | Unclassified → loud-gate abort, exactly as designed: `Error: duo: unclassified meta keys on in-scope entities (loud-and-blocking gate): - post_meta:origin`. | One core-manifest line, `"origin": {"class": "authored"}`. Confirmed by direct inspection this is the *only* postmeta WP writes in this flow — the navigation post, the reusable block, and the template part all carried **zero** postmeta beyond the engine's own `_duo_uuid`. |
| `core/template-part {"slug":"header","theme":"twentytwentyfive"}` | Left **completely untouched** by capture — no `block_attrs` rule matches `core/template-part`, and that's *correct*, because the reference is a portable slug+theme-name pair, not a numeric id. It round-trips for free with **zero** engine work. | **No engine work needed.** (Same theme-mismatch caveat as above: an unrecognized `theme` value on the target env leaves the reference silently inert — inherent to FSE, not Duo-specific.) |
| `core/navigation {"ref":N}` — a template referencing a `wp_navigation` post | Already in `manifests/core.json`'s `block_attrs` (`{"kind":"post","path":"ref","type":"int"}`). Verified end to end: fx2's applied template correctly resolves `ref` to fx2's *local* `wp_navigation` row. | **Already works**, zero new code — just needs the post type added to policy. |
| `core/image {"id":N}` + `wp-image-N` class | Already covered by the existing `IMAGE_CLASS_BLOCKS` list + `block_attrs` registry. Verified: `{{uploads}}` src rewrite correct, attachment byte-identical on fx2. | **Already works.** |
| `core/block {"ref":N}` — reusable-block embed | Already in the registry. Verified: CTA text renders correctly on fx2, sourced from fx2's own local `wp_block` row. | **Already works.** |
| **`core/navigation-link` `"id":N` + `"url":"http://…"`** (and, by identical attribute shape, `core/navigation-submenu`) | **The critical gap.** Neither attribute is touched by capture. `id` has no `block_attrs` rule for this block name, so the raw env-local post id passes straight through. `url` is a plain string inside JSON `attrs`; the URL tokenizer (`tokenize_text()`) only ever walks `innerHTML`/`innerContent` text — it never looks at parsed attribute values — and this block uses **self-closing syntax** (`/-->`, no inner HTML at all), so literally nothing about it is inspected by anything. **Confirmed empirically, not theoretically:** fx2's rendered homepage nav bar links to `http://localhost:8810/duo-fse-about/` — fx1's *own* origin — after a clean apply (canary "clean", zero warnings) and a byte-identical capture→apply→re-capture round trip. Compare the same page's correctly-rewritten `core/image` src and footer `<a href>`, both correctly pointing at fx2's own `localhost:8811`. | **New engine capability, two parts:** (1) a *polymorphic* block-attrs rule — `id`'s ref kind depends on the sibling `kind` attribute (`post-type`→post ref, `taxonomy`→term ref, `custom`→no ref at all). The current `{kind, path, type}` schema has no conditional dispatch; this needs the same kind of bespoke handling `_menu_item_type` already gets in `Capture`/`Apply`'s classic-menu code, generalized to blocks. (2) A "tokenize this attribute like text" declaration — nothing in `block_attrs` today routes a string attribute through `tokenize_text()`/`detokenize_text()`; only `int`/`int[]` id-refs are handled. |
| Round-trip byte-diff as a correctness proxy | fx2's post-apply re-capture is **byte-identical** to fx1's original capture, and `duo apply`'s own canary reported `"clean"`. By every existing acceptance check in this codebase, that's a **pass**. The site is nonetheless broken (cross-environment nav links pointing at the wrong host, plus an id that resolves to the wrong post *type* — see below). | **Cross-cutting methodological finding, not FSE-specific:** byte-identical round-trip is necessary but *not sufficient* once any ref-shaped value is invisible to the tokenizer, because the source and target environments then simply encode the identical wrong bytes. Design finding #9's proposed linter ("flag unclassified option values that equal existing post/term ids") needs to generalize to block attributes: flag any integer-valued or absolute-URL-shaped attribute on a block name with **no** `block_attrs` entry at all, as a loud warning distinct from "no rule matched, nothing to do." |
| Apply phase-1 row-creation order | `Apply::load_tree()` builds its work list from `glob('posts/*/*.md')`, which sorts alphabetically by **post-type directory name** (`attachment` < `page` < `wp_block` < `wp_navigation` < `wp_template` < `wp_template_part`) — not by original creation order. fx1's seed order was about=1, contact=2, attachment=3; after apply, fx2 assigned attachment=1, about=2, contact=3. | This is what turns the navigation-link gap from a theoretical staleness risk into active, silent corruption: fx2's un-rewritten `id:1` (meant "About") now resolves to `get_post(1)` = **the attachment**, not a page. Task #10 (completed) covers *phase-2 finalize* ordering; phase-1 *row creation* order (which determines the actual id space new entities land in) remains undeclared glob-alphabetical. Any manifest/engine work touching raw, un-rewritten ids inherits this amplifier for free — it's not something a future fix can ignore as a corner case. |
| **Manifests cannot declare scope** | `Policy::post_types()` and `Policy::taxonomies()` read *exclusively* from `site.duo.json`'s `policy.post_types`/`policy.taxonomies` — there is no manifest-level aggregation for either (unlike `option_rule`/`post_meta_rule`/`term_meta_rule`, which do loop every pinned manifest). A manifest can only add classification *rules* (meta/option keys, body/phase hints, interpreters, rebuilders, delete-guards) for post types the site has *already* put in scope itself. Confirmed this isn't new to FSE — it's the existing, consistent architecture: spike E's own site policy separately lists `acf-field`/`acf-field-group` in `policy.post_types` even with the `acf` manifest pinned. | **Not a bug — a documentation/DX gap.** Pinning `"manifests": ["core", "fse"]` alone would silently capture *nothing* new; every consuming site repo needs its own `policy.post_types`/`policy.taxonomies` boilerplate alongside the manifest pin. Worth a nice-to-have follow-up: let a manifest declare a *default* scope list a site can opt into with one line, rather than requiring every site to hand-copy the same four post types and three taxonomies. |

## What already works, stated plainly

It's not all gaps: three of FSE's four content types — `wp_template`, `wp_template_part`, and `wp_block` (including a reusable-block embed) — round-trip **correctly today** the moment they're added to site policy, with the existing `core/navigation`, `core/image`, and `core/block` rules doing exactly the right thing, verified by rendering (not just diffing) both before and after apply. The one real blocker is `wp_navigation`'s *contents*, specifically the `core/navigation-link`/`core/navigation-submenu` children.

## Proposed next task

**"FSE block-attrs completeness: polymorphic + string-attr block rules"**

- Extend the `block_attrs` manifest schema to support (a) a `kind_from`/`kind_map` conditional dispatch for sibling-attribute-driven ref kind (needed for `core/navigation-link`/`core/navigation-submenu`'s `id`+`kind` pair), and (b) a `"type": "url"` (or equivalent) attribute kind that routes the value through `tokenize_text()`/`detokenize_text()` the same way `innerHTML` content already is.
- Add `wp_template`, `wp_template_part`, `wp_navigation`, `wp_block` to the core manifest's (or a new `fse.json` manifest's) `post_types` as authored; add `wp_theme`, `wp_template_part_area`, `wp_pattern_category` to `taxonomies`; add `origin` to `post_meta` as authored.
- **Acceptance criteria:** seed this report's fixture (or equivalent) on a fresh env pair; capture → apply → re-capture must stay byte-identical (already true today) **and** the target environment's rendered navigation must link to the target environment's own permalinks, not the source's — i.e. add a *rendering* assertion (curl + grep for the wrong host), not just a byte-diff assertion, to whatever conformance gate eventually covers FSE. A byte-diff-only gate would have passed this fixture today despite the corruption.
- **Stretch:** the generalized capture-time linter described above (flag bare ints / absolute-URL-shaped strings in block attrs with no matching `block_attrs` rule) — this would have caught the `core/navigation-link` gap automatically, without anyone having to already know FSE's internals.
- **Guard:** until the theme-mismatch guard exists, applying a captured `wp_theme`/`wp_template_part_area`-scoped entity onto an environment running a different active theme should at minimum surface a plan-time warning (`wp_theme` term slug doesn't match the target's active `stylesheet` option) — cheap to add, currently silent.

## Draft manifest

`manifests/fse.draft.json` (new file, unvalidated) captures the one genuinely manifest-shaped rule verified in this exploration: `post_meta.origin` as authored. It deliberately does **not** attempt a `block_attrs` entry for `core/navigation-link` — the current schema cannot express the polymorphic kind-dispatch that entry would need without silently mis-typing the `custom`-kind case, so a real manifest entry would be actively unsafe to ship before the engine work above lands. Sites using block-based navigation should not enable this manifest as-is; sites using only templates/parts/patterns (no block nav) are fine today.

Per the scope finding above, pinning this manifest is **not** sufficient on its own — a consuming `site.duo.json` also needs, in its own `policy` block:

```json
"post_types": ["post", "page", "attachment", "wp_block", "wp_navigation", "wp_template", "wp_template_part"],
"taxonomies": ["category", "post_tag", "wp_theme", "wp_template_part_area", "wp_pattern_category"]
```

(exactly what `siterepo/fx1/site.duo.json` carries in this exploration — manifests have no way to ship this for you.)

## Verdict

FSE is the **closest of the three frontiers to branchable**: three of its four content types work today with zero engine changes, purely by riding the existing generic post/term/block-ref machinery once policy is extended. The one real blocker — `core/navigation-link`'s invisible `id`/`url` attributes — is narrow and precisely characterized (one block-attrs schema extension: conditional kind dispatch + string-attribute tokenization), not an open-ended unknown. The sharper risk this exploration surfaced is general, not FSE-specific: Duo's own round-trip byte-diff check would have certified this broken fixture as a clean pass, which means the same blind spot silently threatens *any* future manifest (page builders very much included — see the Elementor report) that captures a block or meta value containing a reference the tokenizer doesn't know to look for.

## Status: implemented (2026-08-05)

Both proposed engine capabilities landed in `agent/src/Grammar/Blocks.php`, generalized (not FSE-specific) for reuse by the Elementor wave:

- **Polymorphic kind dispatch**: a `block_attrs` rule may replace `"kind"` with `"kind_from": {"attr": ..., "map": {sibling-value: kind}, "default"?: kind}`, resolving the ref kind from a sibling attribute's *current* value at rewrite time. Dispatch producing no kind (no map hit, no default) leaves the attribute untouched rather than guessing.
- **String-attribute tokenization**: a rule of the form `{"path": ..., "tokenize": "text"}` routes a plain string attribute through the same `tokenize_text()`/`detokenize_text()` pass body content already gets. Both shapes are additive and fully backward-compatible — every pre-existing `{kind, path, type}` rule is untouched, verified by regression runs.

`manifests/core.json` gained `post_meta.origin` (authored — the only postmeta a customized template/part carries beyond `_duo_uuid`, confirmed empirically; plain `wp_insert_post()` does *not* write it, so a seed exercising this path must set it explicitly the way the Site Editor's REST controller does) and `block_attrs` entries for `core/navigation-link` and `core/navigation-submenu` (`id` via `kind_from` mapping `post-type`→`post`/`taxonomy`→`term`, `url` via `tokenize: text`). `manifests/fse.draft.json` is deleted — its one rule is absorbed above; no separate FSE manifest exists, per the "FSE is core WordPress" framing. `wp_theme`/`wp_template_part_area`/`wp_pattern_category` needed no manifest rules beyond scope inclusion (confirmed: zero extra term meta on any of them).

One report gap closed in passing: the original fixture never actually seeded a `kind:"taxonomy"` navigation link (only asserted the mapping from the block's schema), so the conformance seed adds one. The theme-mismatch guard and `wp_pattern_sync_status` postmeta remain open, exactly as this report flagged — neither was in this wave's scope.

**Acceptance**: `sandbox/conformance/run.sh fse` passes clean-room — byte-identical capture-twice, byte-identical canonical(conf1)==canonical(conf2), clean side-effect canary — *and* a new render-level check (`conformance/checks/fse.sh`) curls conf2's live front page post-apply and asserts the post-type link, taxonomy link, custom-URL link, reusable-block image, and footer link all resolve to conf2's own host, with an explicit negative assertion that conf1's host never appears. This is the render-not-just-byte-diff acceptance the report's own methodological finding called for. `core` and `acf` regressions pass unchanged; `woocommerce` also re-verified as a bonus. `fse` added to the CI conformance matrix.
